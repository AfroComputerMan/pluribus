  <action>
    1. Create `src-tauri/migrations/009_agent_state.sql`:
       ```sql
       ALTER TABLE threads ADD COLUMN agent_status TEXT DEFAULT NULL;
       ALTER TABLE threads ADD COLUMN provider_type TEXT DEFAULT NULL;
       ```
       Use DEFAULT NULL so existing threads are unaffected. agent_status stores one of: 'running', 'error', 'waiting-approval', 'completed', 'queued'. provider_type stores 'agent-sdk' or 'codex'.

    2. Update `ThreadRow` interface in `db.ts`:
       - Add `agent_status: string | null;`
       - Add `provider_type: string | null;`

    3. Enforce WAL mode in `getDb()`: After `Database.load(DB_URL)` resolves, execute `PRAGMA journal_mode=WAL` on the connection. Log if the returned mode is not 'wal'. This ensures WAL persists regardless of migration behavior (per Pitfall 1 from research).

    4. Add new db.threads operations:
       - `updateAgentStatus(id: string, agentStatus: string | null): Promise<void>` -- updates agent_status and updated_at
       - `updateProviderType(id: string, providerType: string | null): Promise<void>` -- updates provider_type and updated_at
       - `listByAgentStatus(agentStatus: string): Promise<ThreadRow[]>` -- SELECT threads WHERE agent_status = $1 AND status = 'regular' ORDER BY updated_at DESC
       - `archiveStaleCompleted(daysOld: number): Promise<number>` -- UPDATE threads SET status = 'archived' WHERE agent_status = 'completed' AND updated_at < datetime('now', '-N days'), returns rowsAffected (for 7-day auto-archive per user decision)

    5. Wire new operations into `db.threads` namespace (following existing pattern).

    Note: Do NOT use the WriteSerializer here yet -- that wiring happens in Plan 03 when the registry orchestrates writes.
